# Personal Website Implementation Specification

**Target repository:** `chengxuan-li.github.io`  
**Deployment target:** `https://chengxuan-li.github.io/`  
**Document purpose:** implementation handoff for coding agents working directly inside the repository  
**Date:** 2026-09-03

---

## 1. Objective

Implement a restrained, technically credible personal website for a PhD-level researcher/engineer working across AI, software, simulation, and energy systems.

The site must serve two overlapping audiences:

1. **Research/academic readers** looking for projects, publications, talks, and research trajectory.
2. **Technical industry readers/recruiters** looking for concrete engineering work, methods, software, technical depth, and a concise CV.

The site is not intended to be a graphic-design portfolio, a conventional faculty homepage, or a long-form blog. It should read as a modern research-engineering portfolio: fast, sparse, technically informative, and easy to scan.

The four top-level pages are:

- **Home** — curated synthesis and first impression
- **Projects** — technical portfolio and project case studies
- **CV** — complete professional record in HTML, with PDF download when available
- **News** — reverse-chronological activity stream

Content must be reusable across these pages rather than independently duplicated.

## 2. Non-negotiable agent rules

### 2.1 Repository access and inspection

Agents have full filesystem access to the repository and may inspect the existing codebase before changing anything.

Before implementation:

1. Inspect the existing repository structure.
2. Inspect package/config files and determine whether a framework or style system is already established.
3. Inspect existing content, assets, workflows, and deployment configuration.
4. Preserve useful existing conventions unless they conflict with this specification.
5. Avoid unrelated refactors.

### 2.2 Git safety

Agents may use **non-destructive Git commands** for inspection, including commands equivalent to:

- `git status`
- `git diff`
- `git log`
- `git show`
- `git branch --show-current`
- `git rev-parse`
- `git ls-files`
- `git grep`

Do not use destructive history or working-tree operations unless explicitly instructed by the user. In particular, do not use force push, hard reset, destructive checkout/restore, branch deletion, history rewriting, rebase, clean, or similar operations.

### 2.3 Commit authorship: strict prohibition on agent attribution

**Agents must never identify themselves, an AI product, or a model as the author, co-author, committer identity, or generated-by attribution of a commit.**

The following names/identities, and equivalents, are prohibited in commit authorship, commit trailers, commit messages, generated-by notices, or repository metadata:

- Claude
- any Claude model name or version
- ChatGPT
- OpenAI ChatGPT
- Codex
- any Codex model name or version
- any other AI agent/model identity

Specific requirements:

- Do **not** set Git `user.name` or `user.email` to an agent/model identity.
- Do **not** use `--author` with an agent/model identity.
- Do **not** add `Co-authored-by:` trailers naming an agent/model.
- Do **not** add “Generated by Claude/ChatGPT/Codex/etc.” to commit messages or files.
- If the repository already has a human Git identity configured, do not replace it.
- If no valid human Git identity is configured and the environment would otherwise require the agent to invent one, **do not create the commit**. Leave the changes in the working tree and report that a human-authored commit is required.
- If the environment only exposes non-destructive Git operations, do not attempt to work around that limitation.

### 2.4 Content integrity

Agents must not fabricate biographical, academic, employment, publication, award, software, conference, date, affiliation, metric, or project information.

All factual site content must be supported by one of:

1. tracked machine-readable reference material under `/references/`;
2. explicit content already present in the repository; or
3. direct user instructions.

If a fact is ambiguous or conflicting, preserve the ambiguity in the reference extraction notes and do not publish an invented resolution.

## 3. Technology choice

### 3.1 Existing stack takes precedence

If the repository already contains a coherent, suitable static-site implementation, continue with that stack rather than replacing it solely for preference.

### 3.2 Default stack for an otherwise empty/minimal repository

If no frontend/site stack has been established, use:

- **Astro**
- **TypeScript**
- static output only
- plain CSS, CSS modules, or a minimal existing style approach

Do not add a large client-side framework unless an existing repository decision requires it.

Reasons for the default:

- static output is appropriate for GitHub Pages;
- content collections suit projects/news/publications;
- project detail pages can be generated from structured content;
- little or no client JavaScript is required;
- good performance and accessibility defaults;
- easy cross-registration of content across Home, Projects, CV, and News.

### 3.3 Avoid unnecessary dependencies

Do not add a CMS, database, server runtime, authentication, analytics platform, animation library, component framework, search backend, or client state-management library for the initial implementation.

The site should remain maintainable as a static repository.

## 4. GitHub Pages deployment

This repository is a **GitHub Pages user site**, not a project site.

The repository name must remain:

`chengxuan-li.github.io`

The deployed canonical root must be:

`https://chengxuan-li.github.io/`

There must be **no repository-name path prefix** in generated internal URLs.

For an Astro implementation:

- configure the canonical site origin as `https://chengxuan-li.github.io`;
- use root-relative/static-site URLs appropriate to a user site;
- do not configure a `/chengxuan-li.github.io/` base path;
- output a static build, normally to `dist/`.

### 4.1 Deployment method

Prefer **GitHub Actions + GitHub Pages** for non-Jekyll/static-framework builds.

The workflow should:

1. trigger on pushes to the default branch and allow manual dispatch;
2. check out the repository;
3. install dependencies reproducibly;
4. run validation/linting if configured;
5. build the static site;
6. upload the generated Pages artifact;
7. deploy using the official GitHub Pages deployment mechanism.

Use current stable official GitHub Actions for Pages at implementation time.

The workflow must have only the permissions required for Pages deployment.

### 4.2 Deployment acceptance test

A deployment is only considered correct when:

- `https://chengxuan-li.github.io/` loads the home page;
- `/projects/`, `/cv/`, and `/news/` work directly when opened by URL;
- individual project pages work directly by URL;
- static resources load from the root site without a repository-name prefix;
- refreshing a nested URL does not produce a deployment-path error;
- all internal links remain inside the canonical root unless intentionally external.

## 6. Reference-material workflow

### 6.1 Purpose

The `/references/` directory is a tracked knowledge base used to ground site content.

The user will place machine-unfriendly source files such as:

- `.docx`
- `.pdf`
- `.pptx`
- exported CVs
- manuscripts
- bios
- award material
- project descriptions
- other source documents

inside:

`/references/archive/`

### 6.2 Git behavior

`/references/archive/` must be Git ignored.

The rest of `/references/`, including extracted machine-readable reference files, must remain Git tracked.

A suitable `.gitignore` rule is conceptually:

```gitignore
/references/archive/*
!/references/archive/.gitkeep
```

A `.gitkeep` may be tracked if useful, but the directory contents themselves must not be committed unless the user explicitly changes this rule.

### 6.3 Agent responsibility for extraction

Whenever relevant new or changed source files are present in `/references/archive/`, the implementation/content agent is responsible for extracting useful information into structured, machine-readable files under:

`/references/extracted/`

Agents should use deterministic/document-aware extraction methods when available rather than manually guessing from rendered text.

The extracted files are **not runtime website content**. They are an auditable intermediate knowledge layer.

### 6.4 Preferred extraction format

Use Markdown with YAML frontmatter by default because it is both human-readable and machine-readable.

Example:

```md
---
id: cv-2026-09
source_files:
  - Chengxuan_Li_CV_2026.pdf
source_types:
  - pdf
extraction_scope:
  - education
  - experience
  - publications
  - awards
  - skills
status: extracted
---

# Education

## Cornell University
- Degree: ...
- Field: ...
- Dates: ...

# Experience
...

# Extraction notes
- ...
```

For strongly tabular material, YAML or JSON may be used instead.

### 6.5 Provenance requirements

Each extracted reference should retain enough provenance to identify where the information came from. At minimum:

- source filename(s);
- extraction scope;
- any ambiguity or conflict notes;
- whether a field is explicit in the source or inferred/normalized.

Do not silently convert uncertain source text into a definite published fact.

### 6.6 Recommended reference index

Create `/references/README.md` describing:

- the role of `archive/`;
- the role of `extracted/`;
- how agents should extract new source files;
- how live site content is promoted from extracted references;
- the prohibition against directly serving archive files;
- naming conventions.

Optionally maintain `/references/extracted/index.md` listing extracted source records and their scope.

The site must use shared structured content. Do **not** hand-maintain separate copies of the same project/publication/event across multiple pages.

Conceptual content types:

```text

Publication
NewsItem
Experience
Education
Talk
Award
```

Every record should have a stable ID or slug suitable for cross-reference.

### 7.1 Relationship model

At minimum support relationships equivalent to:

```text
Project
 ├── Publications[]
 ├── NewsItems[]
 ├── Talks[]
 ├── RelatedProjects[]
 └── Experience? / affiliations as needed

Publication
 └── Project(s)[]

NewsItem
 ├── Project(s)[]
 ├── Publication(s)[]
 ├── Talk(s)[]
 └── Award(s)[]
```

The implementation may normalize relationships one-way internally as long as reverse lookups can be generated reliably.

### 7.2 Content validation

Use schema validation where supported by the framework.

Build-time validation must catch:

- missing required IDs/slugs;
- duplicate IDs;
- malformed dates;
- invalid URLs where practical;
- references to nonexistent projects/publications/news records;
- invalid feature/order fields.

A broken cross-reference should fail the build or emit a clearly actionable build error rather than silently render as a broken link.

## 12. Individual project specification — `/projects/[slug]/`

Individual project pages are the deepest content layer of the site.

They should read as technical case studies rather than generic portfolio cards.

Recommended structure:

1. Project header
2. Hero visual
3. Problem
4. System / Method
5. My Contribution
6. Technical Details
7. Results / Outputs / Visuals as appropriate
8. Publications / Software / Talks
9. Related Work

### 12.1 Project header

Include:

- title;
- one-line project description;
- dates;
- relevant affiliation;
- restrained technical tags;
- available links such as GitHub, Paper, Demo.

### 12.2 Problem

Explain the technical or research problem before describing the implementation.

Avoid opening with a generic sentence such as “X is a software platform...” when a problem statement can provide better context.

### 12.3 System / Method

Use diagrams and visuals where they materially improve explanation.

For complex systems, show architecture/data flow before detailed prose.

### 12.4 My Contribution

This section is required for collaborative projects when individual contribution would otherwise be ambiguous.

Use explicit first-person attribution only where supported by source material.

The purpose is to make technical ownership legible to recruiters and collaborators.

### 12.5 Technical Details

Project-specific subsections are encouraged.

Do not force every project into identical technical headings.

For example, an EnergyAtlas case study might use:

- Simulation Engine
- Data Architecture
- Calibration
- Scalability
- Grid Integration

while an ML project may use a completely different structure.

### 12.6 Outputs

Generate related outputs from structured relationships where possible:

```text
PUBLICATIONS
[related publications]

SOFTWARE
[repositories/packages/demos]

PRESENTATIONS
[related talks]
```

### 12.7 Related work

Show 2–4 related projects when relationships exist.

Do not generate unrelated filler suggestions solely to populate this section.

## 25. Content conflict handling

If two reference documents conflict:

1. record the conflict in the extracted reference notes;
2. prefer the newest clearly authoritative source only when that authority is evident;
3. do not silently merge incompatible values;
4. if the correct public value cannot be determined, omit the disputed value from the live site until resolved.

Examples include conflicting:

- dates;
- job titles;
- publication status;
- author order;
- project metrics;
- award descriptions.

## 28. Error and empty-state behavior

Do not show broken placeholders simply because optional content does not exist.

Examples:

- no GitHub link → omit GitHub action;
- no downloadable PDF CV → omit Download PDF;
- no publications attached to a project → omit Publications section;
- no related projects → omit Related Work;
- no project image → use a restrained designed fallback, not a broken image icon;
- no news for a year → do not render empty year headings.

Optional data should produce graceful omission.

## 33. Guiding principle

The site should be implemented as **multiple views over one structured professional/research knowledge base**:

```text
                         HOME
                           │
                  curated synthesis
                           │
          ┌────────────────┼────────────────┐
          ↓                ↓                ↓
      PROJECTS             CV              NEWS
          │                │                │
   technical story    formal record    chronology
          │                │                │
          └────────────────┼────────────────┘
                           │
                    shared content
                           │
       ┌───────────────────┼───────────────────┐
       ↓                   ↓                   ↓
    Projects          Publications           Events
       ↓                   ↓                   ↓
    Software              Papers          Talks / Awards
```

Home should be selective. Projects should be technically deep. CV should be complete and chronological. News should demonstrate trajectory. The underlying facts and relationships should remain consistent across all four.
